# Spec+TDD 提示词模板

两个模板对应不同职责：**公共模块**负责定契约，**功能模块**负责按契约接入。不要混用——公共模块的 agent 不该关心某个具体活动的参数，功能模块的 agent 不该重新定义契约。

---

## 模板一：公共模块（架构/契约层）

用于：活动系统、货币系统、房间管理等会被多个功能模块依赖的底层模块。

```
你正在开发一个【公共模块】：{模块名}，它会被多个业务功能依赖，
一旦定义就不能轻易破坏性变更。请严格按以下步骤推进，每一步完成后停下等待我确认，
不要跳步。

## 第一步：调研现状
1. 检索现有代码库中是否已存在类似模块或相关契约（路径通常在 contracts/ 或 architecture/ 下）。
2. 如果存在旧版本，先用 3-5 句话总结你推测的现有设计意图和已知约束，
   等我确认或纠正后再继续。
3. 列出可能已经依赖这个模块的功能（通过 grep/AST 扫描代码，不要凭空猜测）。

## 第二步：定义契约（先写 spec，不写代码）
在 contracts/{模块名}.spec.md 中输出以下结构：

### 契约定义
- 对外暴露的接口/字段/类型（用具体类型签名，不用自然语言描述）
- 生命周期钩子及触发时机

### 调用时序
- 用步骤列表或时序图说明各钩子/接口的调用顺序
- 明确失败路径：某一步出错时，系统是跳过、重试还是整体回滚

### 边界情况（显式枚举，不留给实现者猜）
- 至少列出 5 类边界输入/并发场景，每条都要能直接映射成一条测试断言
- 明确写"不做什么"（non-goals），防止后续被顺手"优化"出契约之外的行为

### 接入指南
- 一个可运行的最小骨架示例（no-op 实现即可）
- 已知陷阱/反模式列表（比如"不要在结算钩子里做网络请求"）

写完后停下，等我确认这份契约的边界和非目标是否符合预期。

## 第三步：TDD（角色分离）
确认 spec 后，分两个独立阶段执行，第二阶段开始前不要回看第一阶段的思考过程：

1. 【测试生成】只依据上面的 spec 文档（不看任何已有实现代码），
   为每一条边界情况和调用时序写一条测试。测试要能覆盖 spec 中枚举的所有边界，
   不要为了让测试好写而弱化边界条件。
2. 【实现】依据 spec + 上一步生成的测试来实现，目标是让测试通过，
   不要修改测试来迁就实现。如果发现某条测试和 spec 有矛盾，停下来报告矛盾点，
   不要自行决定以哪个为准。

## 第四步：影响面报告
如果这次修改了已有契约（不是新建），运行一次 grep/AST 扫描，
生成一份"谁在依赖这个契约"的清单，评估这次改动是否是破坏性变更，
并在回复末尾用一句话说明结论。不要把这份清单写入 spec.md 本身
（谁在用是可查询的事实，不是设计意图，不需要人工维护同步）。
```

## 模板二：功能模块（业务/接入层）

用于：具体活动、玩法、运营功能，通常依赖一个或多个公共模块的契约。

```
你正在开发一个【功能】：{功能名}，请先帮我判断它的风险等级，
再决定 spec 该写多重，不要默认写满全套。

## 第一步：判断风险等级
按以下三个问题给出结论（每个给出一两句理由）：
1. 出错代价：会不会造成资损、数据不可逆、需要人工介入才能修复？
2. 复用/生命周期：这个功能或其中的机制会不会被其他玩法复用（哪怕只是"可能"）？
3. 可逆性：出问题后能快速回滚，还是覆水难收？

根据结论给出分级：
- 高风险/会被复用/不可逆 → 走"完整流程"（第二步 A）
- 低风险/一次性/可逆 → 走"轻量流程"（第二步 B）
如果拿不准，默认按"完整流程"处理，不要自行放宽。

## 第二步 A：完整流程（高风险/会被复用）
1. 检索这个功能需要依赖哪些公共模块契约（路径在 contracts/ 下），
   列出你要接入的每一个契约点，不要重新定义已经存在的契约。
2. 在 features/{功能名}/spec.md 中只写"差量"：
   - 引用了哪个公共契约（写路径，不复制契约内容）
   - 这次功能特有的参数/规则/边界值
   - 明确写这次的 non-goals（哪些看起来相关但故意不做的行为）
3. 写完停下，等我确认差量参数和边界值是否符合设计意图
   （尤其是反直觉的数值决定，比如"这个概率是策划特意压低的"，
   必须在 spec 里留一句原因，防止后续被当 bug 改掉）。

## 第二步 B：轻量流程（低风险/一次性）
1. 不写完整 spec.md，直接列出 3-5 条验收标准（每条要能直接写成一条测试断言）。
2. 明确写清楚活动/功能的生效周期，完成后我会把整个目录归档。

## 第三步：TDD（角色分离，同模板一）
1. 【测试生成】只依据上面产出的差量 spec 或验收标准写测试，
   不要参考其他类似功能的实现代码来"脑补"细节。
2. 【实现】依据 spec/验收标准 + 测试来实现。如果发现某个公共契约
   无法满足这次的差量需求（比如缺少某个钩子），停下来报告，
   不要绕过契约直接访问公共模块的内部实现。

## 第四步（仅当是"修改已有功能"而非新建时）
先读现有代码+测试，用 3-5 句话反推你认为的当前设计意图和已知约束，
等我确认后再开始改动，不要直接改。
```

## 使用提示

- 两个模板的核心区别：**公共模块模板强制第四步"影响面报告"，功能模块模板强制第一步"风险分级"**——前者怕改坏别人，后者怕自己该写的没写。
- 如果同一次对话里 agent 既要扮演测试生成又要扮演实现，模板里"不要回看上一阶段思考过程"这句话尽量当真执行（比如开新会话/新 context），否则角色分离形同虚设。
- {模块名}/{功能名} 替换成实际名称即可直接使用。
